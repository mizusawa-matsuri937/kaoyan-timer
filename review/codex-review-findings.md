### C1 — P1：同版本不同内容时，旧编辑器失去并发保护

**位置：** `src/store.ts:414` 只核对 `updatedAt`；`src/store.ts:452` 根据数据库当前版本再生成更高版本。远端相同时间戳的不同内容由 `src/sync/merge.ts:205` 决胜，但胜出的记录仍保留相同 `updatedAt`。页面在 `src/components/SessionEditor.tsx:69` 只传打开时的时间戳。

**触发顺序：**

1. 打开记录 S 的编辑器，保存快照 `updatedAt=T`、科目 `ds`。
2. 同步到另一设备的记录，ID 和 T 相同，但科目为 `os`；确定性规则选择 `os`。或者同步到相同 T 的删除墓碑，墓碑胜出。
3. 不关闭旧编辑器，点击保存。它仍传 `expectedUpdatedAt=T`。

**实际结果：** 检查通过，返回 `true`，旧编辑器内容以 T+1 或更高版本覆盖远端修改。墓碑场景中，`deleted=true` 被改回 `false`。这里不是约定允许的“离线的新编辑胜过旧删除”：应用已经接收了冲突结果，用户持有的打开时快照却没有被识别为过期。

**后果：** 错误覆盖、意外恢复已删记录，之后还会作为更高版本同步。

**建议：** 使用能区分同时间戳不同内容的编辑前置条件，例如完整规范化快照指纹，或包含设备/操作标识的修订令牌；在事务中与数据库当前记录比较。不要把“读取最新 updatedAt”当作用户已看过最新内容。

**复现：** `review/codex.store-review.test.ts:72`、`:85`，均失败。

### C7 — P1：补录按钮重复点击会重复计时

**位置：** `src/components/SessionEditor.tsx:58`、`:66`、`:67`、`:146`。

**触发顺序：** 打开“补录”，填入一段 1 小时记录；点击保存，在第一次数据库提交返回前再点击保存。当前面板尚未关闭，按钮没有保存中禁用状态或立即生效的重入保护。

**实际结果：** 每次回调执行都调用 `uuid()`，两次 `saveSession` 使用不同 ID，因此数据库串行化不会去重。测试保存了 **2 条记录、7,200,000 ms**，预期是 **1 条、3,600,000 ms**。

**后果：** 重复计时、统计翻倍。该提交将保存改为异步等待后，扩大了这个可实际操作的窗口。

**建议：** 为一次补录草稿分配稳定 ID，并在回调入口设置立即生效的在途操作保护，保存期间禁用按钮。只等下一次 React 渲染再改变按钮状态不应成为唯一防线。

**复现：** `review/codex.components-review.test.ts:82`。直接执行实际组件生成的事件回调，使用真实 store 和隔离数据库；这是事件逻辑单元测试，不是浏览器点击测试。

### C3 — P2：跨窗口关闭与上传之间仍有检查/执行窗口

**位置：** `src/store.ts:741` 在 `applyRemote` 事务内检查配置；`src/store.ts:704` 上传前的 `ensure()` 仅检查本标签页 `syncGen`/取消信号，没有跨窗口协调。

**触发顺序：**

1. A 完成远端读取和合并事务，已有上传计划；暂停其提交之后的 JS 继续执行。
2. B 关闭备份，数据库中的 `syncConfig` 已提交为 `null`。
3. A 尚未收到广播，或环境不支持 BroadcastChannel；恢复 A。

**实际结果：** A 仍开始一次 PUT，之后 `finishSync` 才发现配置已关闭。现有用例只覆盖“B 在 A 的 GET 返回之前关闭”，没有覆盖这个后续窗口。

**后果：** 违反关闭后不再开始新上传的要求。该问题不涉及撤销已经送到服务器的请求，因为测试中的 PUT 在关闭提交完成后才开始。

**建议：** 将跨标签页配置变更与请求启动纳入同一协调协议，例如短时跨窗口锁或统一同步执行者。仅重复读一次配置仍有新的检查/执行窗口；BroadcastChannel 通知也不能保证及时交付。无需把网络等待放进 IndexedDB 事务。

**复现：** `review/codex.store-review.test.ts:108`。注入点在真实事务完成之后，没有在事务内部插入外部 Promise，不会人为制造半提交。观察到关闭后 1 次 PUT。真实浏览器中背景冻结/消息延迟的出现频率未测。

### C4 — P2：运行状态与任务生命周期脱节

**三个已确认入口：**

- **配置保存失败：** `src/store.ts:507` 先取消旧任务，随后写配置失败，`:520` 直接返回。原先的 `state.sync.status='syncing'` 没有回退。
- **接收其他窗口配置：** `publishSnapshot` 在 `:215` 使旧任务失效、`running=null`，但 `:225` 的状态选择会在新配置非空时沿用旧 `syncing`。
- **错误元数据也写不进去：** 同步合并遇到配额错误，`recordSyncError` 写入 `syncMeta` 也失败。`:728` 只记录异常；`:787` 的错误状态发布没有执行，内存继续显示 `syncing`。

**具体触发：** 分别模拟在 GET 等待时关闭配置但写入失败、B 切换配置后 A 收到刷新、远端写入和错误元数据写入都遇到配额失败。三个调用最终都已返回/取消，状态仍为 `syncing`。

**后果：** `src/pages/SettingsPage.tsx:201`、`:204` 的“保存并同步”和“立即同步”持续禁用。这里是错误的运行状态，**不是证明 Promise 仍在永久等待**；需要后续成功触发同步或重启页面等操作才能恢复。

**建议：** 在任务失效/退出时独立维护内存运行状态；配置失败后恢复旧配置对应的非运行状态；即使错误元数据无法持久化，也应在内存发布可恢复的错误状态。不能把显示错误的能力依赖于数据库还能写入。

**复现：** `review/codex.store-review.test.ts:138`、`:175`、`:190`。

### C2 — P2：陈旧操作的“已刷新”只有半份状态

**位置：** `src/store.ts:350`、`:352`，导出使用内存的 `:530`。

**触发顺序：** A 开始计时；B 打开并读到相同 active；A 结束并写入 1 小时记录；B 未收到广播时点击结束，被正确识别为陈旧操作。

**实际结果：** B 的 active 被清为 null，并提示“已刷新”，但 B 的 `sessions` 仍为空。此时数据库有 1 条记录，B 的导出 JSON 却是 `sessions:[]`。测试没有在断言前调用 reload。

**后果：** 计时画面暂时丢掉这 1 小时，手动备份漏记录。数据库中的记录仍然存在，再完整 reload 可恢复；不能把它描述为数据库已永久删除。

**建议：** 陈旧拒绝分支读取并发布完整的一致快照，或明确等待完整刷新再开放依赖快照的操作。类似的增量发布路径也应检查跨窗口遗漏。

**复现：** `review/codex.store-review.test.ts:96`。

### C6 — P2：设置失败回滚依赖第二次成功读库

**位置：** `src/store.ts:479` 乐观发布；`:498` 吞掉回滚读取异常；`:499` 无 stored 时不做任何恢复。

**触发顺序：** 修改初试日期 → 设置事务写入失败 → 用于回滚的 `getMeta('settings')` 也失败。存储暂时不可用时，这两个失败可以连续发生。

**实际结果：** `updateSettings` 返回 false，数据库保留旧日期，但界面和 `exportBackupText()` 保留未提交的新日期与新版本号。

**后果：** 内存与数据库持续不一致，用户可能导出从未保存成功的设置。自动同步按数据库读取，因此本测试不证明这个错误值已自动上传。

**建议：** 缓存最后一次成功提交的设置，或把 UI 草稿与已提交设置分离；回滚读库失败时也能撤销本次未提交改动，并考虑连续设置操作的代次，避免回滚覆盖更晚成功的修改。

**复现：** `review/codex.store-review.test.ts:206`。只注入本次写入与回滚读取失败，清除注入后独立查询数据库确认旧值仍在。

### C8 — P2：超时修正仍按同步 API 调用

**位置：** `src/components/OvertimeDialog.tsx:56`、`:74`、`:101` 均忽略 `resolveOvertime` 返回的 Promise，紧接着关闭面板。

**触发顺序：** 先完成一段 1 小时，暂停后继续到超时；在提醒中选择丢弃当前段，保留已完成段；保存发生配额失败。

**实际结果：** store 正确保留原计时器并返回 false，但面板已经关闭。active/settings 的引用没有改变，原 effect 不会因此重新打开面板，用户无法在原修正界面直接重试。

**后果：** 丧失这次修正操作的即时恢复入口，计时器继续运行；之后普通结束可能保存用户原本想丢弃的时间。此处确认的是失败恢复问题，不是事务层已经丢失记录。

**建议：** 等待返回结果，仅成功时关闭；保存期间阻止重复操作，失败保留用户选择及输入供重试。`keep`、`discard`、`endAt` 三个分支都需处理。

**复现：** `review/codex.components-review.test.ts:98`。实际事件函数/实际 store；React effect 调度未做浏览器级验证。

### C5 — P2：合法输入经过本地操作后违反自己的格式约束

**位置：** `src/sync/merge.ts:9`、`:44`、`:52`；`src/store.ts:464`、`:474`。

**触发输入：** 一个其他字段均正常、`updatedAt=MAX_TIMESTAMP=4102444800000` 的 version 1 记录/设置。当前校验明确接受该值，因此不是靠绕过校验构造数据库坏数据。

**记录场景：** 导入后删除，`nextRevision` 产生 `MAX_TIMESTAMP+1`。删除返回成功，但导出的记录被自身 `parseBackup` 标为 `updatedAt 无效`，整体恢复将被拒绝。若该本地记录被推送，后续云端拉取也会遇到同样的校验拒绝（这一后续云端结果由代码路径推导，未访问真实服务）。

**设置场景：** 导入上限版本的设置后，任何正常修改都需要生成上限+1，乐观值校验立即失败，因此设置无法通过正常接口继续编辑；不是“修改成功后丢失”。

**后果：** 极端但已被接受的输入导致备份不可恢复或设置不可编辑。与“2099 年版本永久占优”不同：普通未来版本在被本地看到后，新的本地修改仍可递增并胜出，此控制用例通过。

**建议：** 区分物理时间戳与逻辑修订号的合法域，保证所有被接受的版本经合法操作后仍能序列化、校验和继续编辑；或制定明确的异常版本修复/迁移策略。不能只修复解析端或只修复生成端。

**复现：** `review/codex.store-review.test.ts:155`、`:166`。

## 3. brief 中 12 个疑点的逐条结论

| # | 结论 | 理由与证据 |
|---|---|---|
| 1. 原生 async/await 与 Safari 事务 | **需要真机验证** | 未找到事务内部等待 fetch、定时器或第三方 Promise 的生产路径；`getMeta/setMeta` 仅包装数据库调用，Dexie 官方示例支持原生 async/await，不能仅凭使用 async 判为缺陷。Node 的回滚/并发读用例通过，但不足以证明 iOS 锁屏、异常存储情况下的事务行为。 |
| 2. externalEpoch 过于激进 | **不是问题** | `App.tsx:53` 在 loaded 前不开放操作界面；空库初次发布甚至不会递增代次，只有实际恢复了不同计时器/修订号才会。外部状态变化后拒绝旧点击是有意保护；新增“同标签页 reload 后排队暂停”通过，未发现正常 reload 无故拒绝。实际误拒绝频率没有真机数据。 |
| 3. sameTimer 不比较 ackAt/段数值 | **不是问题（限本版本写入协议）** | 本版本所有计时转换，包括 overtime keep，都会改变 rev 和 timerRev；内容变更不可能仍保持两个修订号不变。新增 ack 测试验证另一页被拒绝并读到新 ackAt。旧版混用/手工改库不遵守此协议，应单列兼容边界，不能声称对任意外部写入都安全。 |
| 4. 设置乐观更新与回滚 | **确认是问题：C6，P2** | 正常情况下队列可能造成短暂显示回退，但提交后的数据库值不会因此被旧 reload 永久覆盖。真正复现的是写入和回滚读同时失败后，未提交值仍可导出。 |
| 5. publishSnapshot 中 invalidateSync | **确认是问题：C4，P2** | 作者描述的同标签页“保存配置+排队 reload”控制用例通过；但接收另一页的新非空配置会取消旧任务，然后保留旧 syncing 状态，恢复按钮持续禁用。因此“调用无害”的广义判断不成立。 |
| 6. 事务内全量 JSON.stringify | **不是问题（就自动提前提交的推测而言）** | 同步 stringify 没有主动等待外部任务，不能仅因耗时长就推断事务提前提交；IndexedDB 的提交条件与事件循环/请求完成有关。这里有主线程延迟、内存峰值和跨窗口事务排队成本，移动端 4 MB 或更大备份仍需性能实测，不能用 Node 数据规模测试替代。 |
| 7. 拒绝未知科目过严 | **不是问题（当前固定科目模型下的显式安全策略）** | 科目 ID 未变，正常界面不会产生未知 ID；未知记录会明确报错，整个文件不写入，符合本轮“坏记录整体拒绝”的策略。新增控制测试确认原本地数据保留。旧版手改备份或未来扩展科目将遇到兼容限制，恢复流程可以另做隔离预览，但不应通过静默丢掉未知记录来“修复”。 |
| 8. 2100 上限/未来版本占优 | **确认是问题：C5，P2** | 上限本身与 nextRevision 不闭合有确定复现；但“2099 版本一直无法超过”不准确，本地见过它后编辑可产生更高版本。未同步的不同设备对未来时钟的处理仍是当前冲突策略的限制。 |
| 9. Dexie 错误重试分类 | **确认是问题：C4，P2；有界重试本身不是无限循环** | 普通未知错误最多 8 次重试，有次数上限。实际缺陷是配额/不可写导致记录错误信息也失败，内存停在 syncing。建议针对配额等需要用户处理的错误减少无效重试，但本轮不把“有限重试可能恢复的错误”单独算作数据缺陷。 |
| 10. 更高版本的离线编辑胜过删除 | **不是问题（约定策略内）** | brief 已接受较新并发编辑可胜出；代码保证较旧/同版本普通记录不能覆盖墓碑，新增控制通过。要改为删除永远优先属于产品冲突语义变更。C1 则是另一个真实问题：已经接收同版本墓碑后，旧编辑器未被拒绝。 |
| 11. 本地 IndexedDB 无超时 | **需要真机验证** | 若底层永不 settle，serial 队列确实会一直等。新增人为延迟完成通知的测试验证阻塞与释放后的恢复，但它是条件性刻画，不证明生产代码存在死锁或 Safari 必然挂起。可增加诊断/看门狗；不能只 Promise.race 超时后就执行下一次写入，因为旧事务可能仍会晚到提交。 |
| 12. useStats 去重缺 hook 测试 | **不是问题（当前计算逻辑），已补部分验证** | 新增用例直接调用实际 useBaseDaily/useLiveDaily：旧半提交 ID 只计一次、其他记录保留、无 active 时统计完整、数据库未被修改，均通过。React 调度/useMemo 被测试替身替代，所以这不是对挂载、缓存失效、真实重渲染或 Safari 的完整证明。 |

上述“不是问题”是对具体疑点和当前协议的判断，不代表该模块没有其他缺陷。

## 4. 测试本身的审查，尤其两个 R1 用例

### 两个改写 R1 用例的结论

**没有发现为了通过测试而放宽原业务要求；改写方向合理，但证明范围不能表述成已经模拟了真实进程崩溃。**

- 原用例在单次表操作前等待测试外部 Promise。在真实事务里这样插入等待，会改变事务存活和 Dexie 上下文，不能继续把观测结果直接当作生产写入边界。官方文档也明确提醒事务内不要等待无关异步 API。
- 新 `crashAt` 用 `Dexie.Promise.reject` 在 Session、activeTimer、syncMeta 写入点失败，特别是后两个点能检验前面已执行写入是否一起回滚；这不是把期待失败改成期待成功。
- `review/store.review.test.ts:209`、`:210`、`:211` 要求原 active 存在且完成 Session 不存在；`:235`、`:236` 同样要求换科目整体回滚，重试后再检查精确时长。比单纯检查最终操作返回值更有意义。
- `review/fix.regression.test.ts:122` 的另一个 Dexie 连接，以只读事务取得配对快照，检查 60 次换科目的 active 与历史记录关系，为中间可见性提供了独立补充。

**确实存在的测试证据缺口：**

1. 两个改写 R1 用例在检查内存前调用了 reload（`:204`、`:230`），因此它们单独不能证明“失败返回时内存就已经正确”。本轮新增四个写入点的测试，在任何 reload 前直接检查内存和数据库，全部通过，并补了原测试未单列的 timerRev 点。
2. Promise 拒绝证明应用处理数据库错误后的回滚行为，不等同于 OS 杀进程、磁盘持久化丢失或 Safari 崩溃恢复。修复总结中的“等价于进程退出”应收窄为逻辑故障模拟。
3. 并发读用例跳过所有 `active=null` 快照（`:157`），所以单独使用它不能排除中途错误清空 active 的实现。还需要结束/开始边界和失败回滚测试一起覆盖。
4. 随机双标签页测试 `review/fix.regression.test.ts:240` 丢弃各操作的返回值；`:246` 没把正在运行的 live 段纳入，`:248` 只检查总时长“不超过”经过时间。它证明部分不重叠/上界，不是精确“总时长守恒”；假如随机操作大量被拒绝甚至全无效果，这部分断言可能仍成立。应加入独立模型、成功/拒绝统计、live 段以及精确预期。
5. 部分 R3 用例在比较内存与数据库前主动 reload，例如 `review/fix.regression.test.ts:291`，会遮住短暂发布错误。C2 的新测试故意不 reload，便发现了导出不完整。
6. 既有测试未执行实际异步组件回调，也未覆盖相同时间戳胜出后的旧编辑器提交、合并完成之后跨窗口关闭、错误状态持久化再次失败。C1/C3/C4/C7/C8 填补了这些窗口。

因此，保留原 136 项作为回归基础是合理的，但“136 全通过”不足以推出全部健壮性目标达成。

## 6. 未覆盖风险与约束核对

- **需要设备证据：** iOS Safari/主屏幕 PWA 杀后台、锁屏、低存储、存储回收、事务原生挂起、真实 BroadcastChannel 顺序、Service Worker 升级及旧新版本同时运行。没有进行这些真机测试。

- **不支持任意历史坏数据：** 已在旧数据库中的未知科目、损坏 active、非法设置，以及旧版仍在写入但不递增修订号的情形，尚无完备迁移/修复测试。显式拒绝未知科目是当前策略，恢复体验仍需产品决定。
