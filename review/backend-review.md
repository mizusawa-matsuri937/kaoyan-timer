# 考研计时器数据层健壮性审查

审查日期：2026-11-09（Asia/Taipei）。代码基线：`d22d65e`。

结论：正常计时和汇总的基础逻辑较稳，但目前不能据此保证长期使用时的数据安全。测试确认了 8 类缺陷，其中 4 类可造成记录丢失、重复计时或错误覆盖，应优先修复。

项目是纯前端 PWA，没有独立服务器。本次“后端”审查覆盖 `store.ts`、计时状态机、IndexedDB 持久化、GitHub 同步、导入导出和日期统计，不评价 UI 设计。

### R1：结束/换科目的数据库操作不是一个事务

**已复现：**

- 开始计时 1 小时后结束，在保存 Session 的数据库事务中注入 `QuotaExceededError`。最终 `activeTimer=null`，Session 也不存在；重新读取数据库无法恢复这 1 小时。
- 在清除 `activeTimer` 已提交、Session 尚未写入的边界暂停执行。此时数据库两边均没有可恢复记录，证明存在进程退出时的丢失窗口。
- 换科目时顺序相反：先写旧 Session，后写新 `activeTimer`。中间状态同时保留旧计时器和同一 ID 的已完成记录；重新打开后，实时汇总会把同一段同时作为历史和正在进行的计时统计。

`resolveOvertime` 的结束分支也沿用“先清 active，再保存 Session”的路径，具有同类代码风险；本轮直接执行的故障用例集中在 `stop` 和换科目。

**原因：** Promise 队列只保证操作先后，不能使两次数据库提交成为不可分割的一次提交。成功提示也早于写入结果。

**建议：** 在一个覆盖 `sessions`、`meta` 的读写事务中完成旧记录结算、新 active/清除 active、dirty 元数据更新；提交成功后再发布成功状态。失败时保留可重试的原计时器。对“太短不保存”的分支单独保留预期行为。

### R2：旧标签页能够结束并清掉新计时器

**复现顺序：** A 开始数据结构 → B 打开并读到此计时器 → A 结束数据结构并开始操作系统 → B 使用旧内存状态点击结束。

**实际结果：** B 把共享数据库中的操作系统计时器清成 `null`，并以较晚的结束时间重写旧的数据结构记录。

**原因：** 每个标签页有自己的 `state` 和 `chain`，写入前不核对数据库里的当前 `sessionId`。`visibilitychange` 只提供偶尔的刷新，不能保护两个同时可见的窗口或刷新尚未完成时的点击。

**建议：** 在跨标签页可串行化的事务中读取当前 active 并核对 ID/修订号，再执行状态转换；陈旧操作应拒绝或重新基于当前状态计算。可用 Web Locks 协调操作、BroadcastChannel 通知刷新，但通知本身不能代替事务和版本检查。

### R3：旧的异步结果覆盖新操作

**前台重读路径已复现：** 先取得“正在计时”的数据库快照 → 用户在第 1 小时点击暂停 → 旧快照返回并覆盖内存 → 第 2 小时点击结束。最终持久化 **2 小时**，正确应为 **1 小时**。

**远端拉取路径已复现：** 拉取到较新记录后，在 `bulkPut` 完成前删除该记录。删除操作写入了较新的墓碑，但随后 `upsertSessionsInState(toLocal)` 无条件把旧的非删除记录写回内存。实测此时数据库 `deleted=true`、内存 `deleted=false`，显示和后续备份可能使用不同版本。

**原因：** `await chain` 只等待读取开始前的写入；在后续 `await` 期间仍允许新的操作发生。合并决策和发布状态没有一起受串行化/版本检查保护。导入的 `bulkPut` 后发布也使用类似代码，需一并审查。

**建议：** 将“读取当前版本→决定合并→提交→发布”作为完整状态操作协调；回到前台的读取用操作代次判断是否已过期。同步在网络读取后重新以最新本地状态合并，而不是直接发布之前算好的 `toLocal`。代次必须覆盖暂停、继续等 active 变化，不能只复用当前仅针对部分变更的 `localVersion`。

### R5：坏数据能越过校验并覆盖好数据

**最直接的复现：** 本地有 1 小时记录，导入同一 ID、较新 `updatedAt`、但时间段结束早于开始的记录。校验认为其有效，`normalize` 把时间段过滤为空，再按较新版本覆盖本地。实际时长从 **3,600,000 ms 变成 0**。

其余失败用例确认：

- 时间戳超出 JavaScript Date 的有效范围仍被接受。
- 合法 JSON 数字 `1e400` 被解析成 `Infinity` 后可作为 `updatedAt`，这种记录会压过正常有限版本。
- 设置只检查 `examDate` 是字符串，`startDate:null`、非数值 `overtimeHours` 仍能进入结果。
- `version:999` 未被拒绝，也没有对应迁移流程。

**建议：** 先完整验证备份版本、记录和设置，再允许合并。检查有限且合法的时间戳、日期、字段类型；正常非删除记录在规范化后不能没有有效时间段。坏记录要拒绝或隔离并向调用方报告，不能静默变成可覆盖好数据的“空记录”。墓碑允许保留的字段应明确区分。导入应避免产生半成功、半失败的状态。

### R4：同步不能可靠地自行恢复

**已复现：** 模拟请求一直挂起，推进 15 分钟后 Promise 仍未结束。当前 fetch 没有 AbortSignal/应用层截止时间，`running` 仍被占用时后续同步只返回同一个任务。

另一个用例中，`navigator.onLine=true`，首次请求发生瞬时网络错误，之后模拟服务恢复。页面持续打开并推进 1 小时，仍只有首次请求，没有重试。当前后续触发依赖新的编辑、页面切回前台、online 事件或用户手动操作。

**建议：** 为 GET、raw GET、PUT 和错误体读取设置可取消的请求期限；在 `finally` 中释放运行状态。对暂时性的网络错误/5xx/限流使用有上限的退避重试，处理 `Retry-After`；401 等配置错误提示修正，不无限重试。页面恢复时重新检查待同步状态。

### R6：系统时间不是可靠的同步版本

**已复现：** 两边同一 ID 的 `updatedAt` 相同，但一边编辑、一边删除时，双方都保留自己；`remoteChanged` 也可能为 false。设置在相同时间戳下存在同样的不收敛。

另一个用例先在快 1 小时的时钟下保存并备份，校正时钟后删除记录；删除的 `updatedAt` 比远端旧记录更小，下次同步将旧记录恢复为未删除。

**建议：** 用明确的修订/逻辑时钟与稳定冲突决胜规则，保证同一设备的新操作不倒退，也保证两端合并得出相同结果。墓碑冲突策略要明确。只有把 `Date.now()` 换成随机值或简单“相等取本地”，不能解决此问题。

### R7：设置单独导入后不会自动备份

**已复现：** 先完成一次同步，再导入只有较新初试日期、没有新 Session 的备份。设置保存成功，但 1.5 秒调度周期后没有上传，dirty 也没有因该变化更新。后续重新打开或其他操作可能偶然触发上传，但当前操作没有履行自动备份预期。

**建议：** 接受设置变更并持久化时也调用标脏/调度逻辑，并纳入正在进行的同步版本检查。

### R8：关闭备份不使已有任务失效

**已复现：** 在远端 GET 等待时关闭备份，随后 GET 返回。旧任务仍拿启动时捕获的配置执行 PUT。完成分支也没有核对配置是否仍有效，可能把状态改回 `ok`。

**建议：** 配置变更时递增同步代次并取消当前请求；各个 `await` 返回后、尤其上传前，检查代次/配置是否仍有效。关闭时清掉排队重试和定时同步。这里要求阻止的是关闭后才开始的上传；已经送到服务器的请求无法保证撤回。

## 通过的重点场景

- 运行计时器经 JSON 序列化、模块重载和 30 天时间跳跃，按时间戳恢复正确。
- 暂停 180 天不增加学习时长。
- 3 个固定种子、每个 10,000 次随机操作，均与独立累计模型相同；各种子实际经历了超过 1,000 次暂停和 1,000 次恢复。
- 500 次快速开始/暂停/继续/结束，经数据库串行写入后保留 500 个唯一记录且总时长正确。
- 跨午夜、跨闰年及纽约 23/25 小时的夏令时日期切分正确。
- 5 年、每天 12 段、共 21,900 条记录的导出/解析/合并/汇总结果一致，JSON 为 4,348,628 bytes（约 4.15 MiB）。这是 Node 下的数据规模验证，不是 Safari 性能保证。
- 2,000 次实时汇总没有修改归档统计；1,000 次旧版本合并没有击穿较新的删除墓碑。
- 导入幂等、离线记录后再同步、409 冲突重拉合并、有界冲突重试及之后手动恢复均通过。
- 单次数据库写入失败后，后续正常写入能够继续，说明队列没有整体停死；这不消除 R1 的结算数据丢失。
- 模拟 HTTP 401/403/429/500/502/503、非 JSON 错误、中文和 emoji、base64 换行、3 MB UTF-8 上传、raw 内容回退均按对应测试预期处理。

## 验证边界与参考

这不是实际连续运行数月的浏览器耐久测试，也没有执行 iOS 杀后台、Safari 存储回收、低存储空间、真实服务端限流、Service Worker 升级或浏览器堆内存泄漏测试。因此不能把通过的时钟/数据规模测试解释为这些平台行为已经得到保证。

GitHub 的大文件读取边界也需要后续真实服务集成验证。本轮验证了“返回 encoding=none 后读取 raw”的代码分支和大文本编码，没有向真实仓库传输多 MB 文件。GitHub 官方文档对 1–100 MB 文件指定 raw/object 媒体类型，而当前首个请求使用通用 JSON Accept；该兼容性仍待实测，未计入上述 8 类已复现缺陷。

正在进行的 activeTimer 不进入当前 JSON/GitHub 备份，这是现有备份范围的限制；本轮验证的是其本地持久化恢复。
