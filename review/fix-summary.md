## 总体设计

1. **状态操作 = 一个完整事务**。每个会改动数据的操作（计时转换、编辑、删除、设置、导入、同步合并）都按"读取数据库当前状态 → 决定变更 → 在一个 `sessions`+`meta` 读写事务里提交 → 提交成功后才发布到内存"执行。本标签页内由串行队列排队；跨标签页由 IndexedDB 读写事务串行化。
2. **数据库是权威**，并在事务里核对版本：计时器修订号 `rev`、全局计时修订号 `timerRev`、记录的 `updatedAt`、同步改动序号 `seq`、同步配置。
3. **网络请求从不放进事务或队列**。同步只在"拿到远端结果之后"排队一次合并事务，并基于此刻数据库的最新状态重新合并。
4. **用户操作的时间在点击时捕获**，排队延迟不改变计时时长。

## R1：结算原子事务

- `stop`、换科目（`selectSubjectAndStart`）、`resolveOvertime`（保留/改结束时间/丢弃）都走 `timerOp`。同一个读写事务内完成：读取并核对当前计时器 → 写入完成的 Session → 写入新计时器或清除 → `timerRev+1` → 标记待同步（`syncMeta.dirty/seq`）。任何一步失败，整个事务回滚。
- 成功提示和内存状态都在提交成功之后才发布。失败时内存与数据库都保留原计时器，并提示"保存失败"，用户可以直接重试。重试时不会重复累计：同 id 只有一条记录。
- 保留"太短不保存"（<1 秒）规则：照样清除计时器，但不写记录，也不标记待同步。
- 兼容旧版本留下的半提交状态（同时存在计时器和同 id 记录）：结束时覆盖为一条记录；统计 hook（`useBaseDaily`）在计时中会排除与计时器同 id 的记录，避免重复统计。

## R2：多标签页竞争

- 事务内以数据库为准做三重核对：计时器 `sessionId`、计时器 `rev` 及运行状态，以及全局 `timerRev`。只要另一个标签页做过任何计时转换，哪怕是"开始又结束、最后回到 null"，`timerRev` 都会变化，于是本标签页的陈旧操作会被拒绝。拒绝后会刷新为最新状态，并提示"其他窗口已更新计时…请再操作一次"。
- 每个标签页记录一个"外部刷新代次"。如果点击之后、执行之前，内存中的计时器被其他标签页的结果替换，说明用户操作的是过期画面，该操作同样拒绝。修复中由随机双标签页测试发现的问题：点击时间早于另一标签页已提交的转换，导致时间段重叠、重复计时。
- 记录的编辑和删除带上打开时的版本（`expectedUpdatedAt`）。版本不一致时拒绝，不会覆盖其他窗口刚改过的记录。
- `BroadcastChannel` 只用于通知其他标签页重新读取（在 `installGlobalListeners` 中创建，测试环境不启用），正确性不依赖它。

## R3：异步结果不覆盖新操作

- `reloadFromDb`（回到前台、广播触发）也在队列中执行，并在一个只读事务里读取完整快照，之后发生的操作会排在它后面执行。
- 同步拉取完成后，不再直接发布之前算好的 `toLocal`，而是排队执行 `applyRemote`：在事务里读取本地最新记录和设置，与远端合并、写回，生成上传内容，并记下 `seq`；发布的内存状态就是事务内的合并结果。
- 上传完成后，`finishSync` 在事务里比对 `seq`。期间有新的本地改动时，保持 `dirty` 并再同步一轮（最多 3 轮，之后转为延迟调度）。
- 操作时间在点击时捕获。测试覆盖了"队列被拖延 2 小时，结束仍按点击时刻计算"，以及内存、数据库、导出备份、上传内容四者一致。

## R4：超时、取消与有上限的退避重试（`src/sync/github.ts`、`src/store.ts`）

- 每个请求都有 `AbortController` 截止时间（GET 30 秒，PUT 60 秒），覆盖响应体读取，包括错误体。即使底层 `fetch` 不理会 AbortSignal，也会通过竞速在超时或取消时立即结束，落败的 Promise 已做吞并处理，不会产生未处理拒绝。
- 网络错误、超时、5xx、408/429、带限流信息的 403、冲突重试用尽，按 5s × 2ⁿ 退避（上限 15 分钟，+20% 抖动），最多自动重试 8 次。`Retry-After`（秒数或 HTTP 日期）和 `x-ratelimit-reset` 会被遵守，单次等待上限 1 小时。
- 401、无限流信息的 403、404，以及云端数据损坏或版本不支持，都视为明确错误，不自动重试。
- 失败时保留 `dirty`，并写入 `lastError`。之后回到前台、`online` 事件、新的编辑或手动同步时会继续。退避期间新的编辑不会额外触发请求。
- 同一时刻只有一个同步任务，并发触发会共享同一个任务；所有退出路径都会在 `finally` 中释放运行状态。

## R5：导入与远端数据校验（`src/sync/merge.ts`）

- `parseBackup` 先做文件级校验：必须是 JSON、`app` 正确、`version` 必须是 1（缺省按 1 兼容早期备份；2、999 等会给出"版本 X 不受支持，请先更新应用"）。设置会完整校验：日期是合法日历日、`overtimeHours` 是 0.5—24 的有限数、`keepAwake` 是布尔值、`updatedAt` 合法。设置损坏时直接抛错。
- 记录逐条校验：id、已知科目、`updatedAt`/`createdAt` 必须是 [1970-01-01, 2100-01-01] 内的有限数，`source`/`deleted` 类型正确，时间段必须是范围内且结束晚于开始的有限数，非删除记录必须至少有一段。损坏记录会被隔离到 `invalid` 并附带原因，绝不会被规范化成会覆盖正常记录的空记录。
- 墓碑单独处理：只要 id、科目、版本合法就保留删除语义，时间段损坏时置空（墓碑不参与统计）。
- 调用方严格拒绝：
  - 导入时只要有任何损坏记录就整体不写入，并提示"备份中 N 条记录已损坏（第 k 条：原因），为避免覆盖现有数据，本次没有导入任何内容"，不会出现半成功的状态。
  - 云端备份损坏或版本不支持时，暂停上传，给出明确错误，不重试，也绝不覆盖云端。
  - 本地保存（`saveSession`）走同一套校验。
- 正常的 version 1 备份照常导入；重复导入幂等；墓碑语义保留。

## R6：版本与冲突收敛

- **逻辑时钟**：新版本 `updatedAt = max(当前时间, 该记录已见过的版本 + 1)`，用于记录的编辑、删除、结算以及设置。系统时钟被往回校正后，新操作的版本仍大于旧版本，删除不会被旧远端记录复活。没有新增字段，`updatedAt` 仍是数字，因此旧备份和尚未更新的旧版本 App 都能读写。
- **确定性冲突规则**（`compareSessions` / `compareSettings`）：版本大的胜出；版本相同时墓碑胜出；仍相同时按规范化内容的字典序决胜。合并满足交换律和结合律（随机属性测试 3×300 轮，故意制造大量相同版本），两端最终收敛。

## R7：只导入设置也会同步

导入只要改变了设置，就在同一事务里标记 `dirty/seq+1` 并调度同步。`updateSettings` 同样处理。上传进行中修改设置时，`finishSync` 发现 `seq` 已变化，会再推送一次。

## R8：关闭或切换备份立即失效

- `setSyncConfig` 会先递增同步代次、取消当前请求，并清除排队的同步和退避重试，然后才持久化新配置。
- 旧任务在每个 `await` 之后（尤其上传前）都核对代次和取消信号。`applyRemote`/`finishSync` 还会在事务里核对数据库中的配置，覆盖"另一个标签页关闭了备份"的情况。失效的任务会静默结束，不会把"已关闭"改回"已备份"；跨标签页的情况会重新读取配置。
- 关闭之前已经发到服务器的请求无法撤回，但关闭之后不会再开始新的上传，这一点已由测试验证。

## 测试调整与新增

### 调整的原审查用例（两个，名称不变）

`[R1] stop must leave a recoverable timer…` 和 `[R1] switching subject must not expose…` 原来把单个表操作挂在测试外部的 Promise 上，以此观察两次提交之间的窗口。事务化之后这种注入与实现冲突：IndexedDB 事务不能跨外部等待保持打开。我用诊断用例证实，被延迟的写入会在 Dexie 事务区之外以独立的隐式事务执行，所以测到的是测试自己制造的拆分。按旧方式运行时，换科目用例中途能看到"旧计时器 + 已保存记录"，但操作本身成功、最终数据正确，而这个中间状态在真实事务中不可能出现。

改为在同一提交边界让事务中断（`Dexie.Promise.reject`，等价于进程在两次写入之间退出或写入失败），并对每个写入点（Session、activeTimer、syncMeta）分别注入。原业务不变量保持不变，断言反而更严格：

- 数据库里始终保留可恢复的计时器；
- 旧计时器和它的完成记录绝不同时存在；
- 中断后整体回滚，内存与数据库一致，重试成功且只有一条记录。

在基线代码上，这两个改写后的用例分别在"可恢复计时器"（第 209 行）和"回滚到旧计时器"（第 235 行）这两个不变量断言处失败，说明它们能检出原缺陷。

另外两个 R3 原用例同样使用外部 Promise 注入，未作修改，修复后通过。它们验证的是"读取/拉取期间发生的操作不被覆盖"这一排队与发布不变量；事务原子性的证明由上述 R1 用例和并发读者用例承担。

## 尚未验证的平台行为与剩余风险

- **不是真机或长期耐久验证**。以上全部基于 Node + fake-indexeddb + 虚拟时钟，没有在 iOS Safari 或主屏幕 PWA 上做过杀后台、锁屏数小时、低存储/配额、存储回收、Service Worker 升级、连续数月运行或内存泄漏测试。
- Dexie 事务内使用原生 async/await，依赖 Dexie 的 zone 机制。Node 中已验证；Safari 上的行为属于 Dexie 官方支持范围，但本次未在设备上实测。
- `BroadcastChannel` 刷新（iOS 15.4+ 支持）只在浏览器中启用，没有自动化测试。正确性不依赖它，没有它时会在回到前台时刷新。
- 真实 GitHub 的限流响应头、大于 1 MB 文件的 raw 读取、真实网络的超时与取消，没有对真实服务做集成测试。
- 冲突语义是"最后写入者胜出"（基于逻辑时钟）。两台设备在都没同步的情况下分别修改同一条记录时，版本大的一方胜出；如果一台删除、另一台随后编辑，且编辑的版本更大，记录会以编辑后的内容保留。逻辑时钟只保证"看过的版本之后的修改一定更新"。
